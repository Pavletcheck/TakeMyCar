# Ревью M1 — `src/main.ts` (прототип M0.5)

- **Дата:** 2026-11-23
- **Ревьюер:** `architect`
- **Объект:** `src/main.ts`, 404 строки, коммит-состояние этапа M0.5 → M1
- **Связано:** `docs/ARCHITECTURE.md` §6 (миграция), `docs/adr/0002-fixed-step.md`

## Вердикт

Прототип решает задачу M0: серый город, машина, езда по WASD, 60 fps. Как каркас он
годится, но **переносить в M1 его как есть нельзя**: цикл без интерполяции, пауза
на одном флаге и коллизии с аллокациями в кадре упрутся в бюджеты уже на M2
(300 коллайдеров). Ниже — 10 замечаний, каждое привязано к строке.

Шкала: **Blocker** — ломает этап; **High** — нарушает бюджет/контракт, чинить в M1;
**Medium** — чинить при переносе файла в систему; **Low** — гигиена, можно после.

## Детали

### R-01 — High. Пауза на одном флаге

`src/main.ts:345–353`

```ts
document.addEventListener('visibilitychange', () => { paused = document.hidden; });
window.addEventListener('blur', () => { paused = true; });
window.addEventListener('focus', () => { paused = false; });
```

**Проблема.** Причин паузы минимум четыре: потеря фокуса, скрытая вкладка, меню,
реклама/`game_api_pause` платформы. Один флаг означает, что последнее событие
побеждает: `focus` снимает паузу, даже если вкладка всё ещё скрыта или открыта
реклама. Обратный случай — `visibilitychange` с `hidden=false` размораживает игру
посреди рекламной паузы.

**Риск.** Физика идёт под рекламой (M8 — нарушение правил платформы), таймеры
миссий тикают в свёрнутой вкладке, а на возврате — рывок.

**Рекомендация.** `GameLoop.pause(reason)/resume(reason)` с множеством причин
(`docs/ARCHITECTURE.md` §3.1). `app/lifecycle.ts` транслирует `blur`, `visibilitychange`
и события платформы в `pause('blur' | 'hidden' | 'platform' | 'ad')`.

### R-02 — High. Нет интерполяции рендера

`src/main.ts:316–318` (запись позиции в фикс. шаге), `src/main.ts:371–393` (цикл)

```ts
carGroup.position.set(car.x, 0, car.z);   // внутри updateCar(STEP)
...
while (accumulator >= STEP && steps < 8) { updateCar(STEP); ... }
renderer.render(scene, camera);
```

**Проблема.** Позиция меша обновляется только целыми шагами 1/60. На 144 Гц
некоторые кадры не содержат шага, и картинка повторяется; на 30 fps шаг
выполняется 0 или 2 раза за кадр — движение «дёргается». `accumulator` уже
посчитан, но в рендер не передаётся.

**Риск.** Критерий M1 «60 fps, езда плавная» формально выполняется, но на телефоне
(30 fps) и на 120/144 Гц игра выглядит хуже, чем есть. Это самый заметный
визуальный дефект.

**Рекомендация.** Хранить `prevX/prevZ/prevHeading`, передавать `alpha` в `onRender`,
интерполировать позицию и кратчайшую дугу курса (ADR 0002). Телепорты (reset,
спавн) — `prev = cur` в том же тике.

### R-03 — High. Коллизии: O(n) и аллокации в шаге

`src/main.ts:236–258` (`resolveCircleRect` возвращает новый `{x, z}`),
`src/main.ts:299–306` (цикл по всем коллайдерам)

**Проблема.** На каждый шаг — линейный проход по всему массиву, и на каждое
касание — новый объект. Сейчас коллайдеров 24, к M3 будет 300+ статических и 50
движущихся: ~18 000 аллокаций в секунду только на физику плеера. Второй цикл
`for (const rect of colliders)` применяет разрешения последовательно, поэтому
углы и стыки зданий «продавливают» объект и вызывают дрожание.

**Риск.** GC-паузы, просадки ниже 60 fps, застревание в углах кварталов —
прямое нарушение критерия M2.

**Рекомендация.** `core/spatialHash.ts` (ячейка 8 м) + `queryColliders(area, out)`.
Узкая фаза уже есть в `core/math.ts`: `circleRect(cx, cz, r, rect, contact): boolean`
заполняет переиспользуемый `Contact` (`nx`, `nz`, `depth`) и не аллоцирует — нужно
только переписать цикл на broadphase и применить контакт по нормали. Разрешение —
2–4 итерации, при нескольких контактах усреднять нормали (см. ADR 0003).

### R-04 — Medium. Аккумулятор и переполнение подшагов

`src/main.ts:377–390`

```ts
const dt = lastTime === 0 ? 0 : Math.min((time - lastTime) / 1000, 0.1);
accumulator += dt;
while (accumulator >= STEP && steps < 8) { ... }
```

**Проблема.** При `steps === 8` цикл выходит, оставляя `accumulator` большим.
Следующий кадр снова упирается в лимит — «догоняние» растягивается на несколько
кадров, управление запаздывает. Обратный случай: после 10-секундного зависания
`dt` уже клампится до 0.1, но 6 шагов подряд — это рывок на 0.1 с игрового времени.

**Риск.** Неприятный «резиновый» ввод после просадки; нет диагностики, что
симуляция отстаёт.

**Рекомендация.** `MAX_SUBSTEPS = 5`, при переполнении `accumulator = 0` и
инкремент `overrun` в debug-HUD; `maxFrameDelta = 0.25`; на паузе аккумулятор
обнулять (ADR 0002, §эталонная реализация).

### R-05 — Medium. Камера и свет живут в кадровом времени

`src/main.ts:321–331`, вызов на `src/main.ts:388`

**Проблема.** `updateCamera(dt)` получает кадровую дельту и читает `car.x/z` —
состояние последнего фикс. шага, без интерполяции. Камера сглажена лучше, чем
объект, за которым следит, поэтому при 30 fps камера «уезжает» от машины.
`sun.position` и `updateMatrixWorld()` переставляются каждый кадр, хотя свет
нужен только для теней вокруг игрока.

**Риск.** Расхождение камеры и цели, лишняя работа в кадре, дёргание shadow-фрустума
(мерцание теней на краях).

**Рекомендация.** `core/camera.ts` считает целевое состояние (позиция, упреждение
по скорости, зум, тряска) из интерполированного состояния; `render/scene.ts`
применяет его и обновляет `sun`/shadow-камеру с шагом, кратным 0.25–0.5 м
(квантование), чтобы тени не «плыли».

### R-06 — Medium. Ввод: сырые клавиши в физике и побочный эффект в обработчике

`src/main.ts:216–233`, `src/main.ts:263–267`

```ts
if (event.code === 'KeyR') resetCar();     // side effect прямо в keydown
...
const throttle = keys.has('KeyW') || keys.has('ArrowUp') ? 1 : 0;
const handbrake = keys.has('Space');
```

**Проблема.** Физика знает про конкретные клавиши — значит, геймпад и тач требуют
правок в физике. Сброс машины вызывается из обработчика события, минуя паузу,
игровой тик и будущую отмену/подтверждение. Нет `wasPressed` (фронтов) — на
подшагах 2+ действие «нажато» повторно. `keys` пополняется любым `event.code`,
включая модификаторы.

**Риск.** Переписывание физики в M4/M6, невозможность мобильного управления без
костылей, случайный респавн во время рекламы/меню.

**Рекомендация.** `core/input.ts` с `ActionId` и привязками в `config/ui.json`
(ARCHITECTURE §3.2); `resetVehicle` — как действие `interact`+`debug`, обработанное
в системе; `beginTick/endFrame` для фронтов; `clear()` на паузе.

### R-07 — Medium. Побочные эффекты на уровне модуля

`src/main.ts:33–34` (`getElementById` + `throw` при импорте),
`src/main.ts:79–168` (генерация города при импорте),
`src/main.ts:334–336` (скрытие `#loading` синхронно при импорте)

**Проблема.** Модуль нельзя импортировать в тесте или в Node — он сразу требует
DOM и WebGL. Генерация города выполняется до первого кадра, поэтому «загрузка»
скрывается раньше, чем сцена готова. Порядок «render → config → world → loop →
platform.ready()» нигде не зафиксирован, а для Яндекса он обязателен
(`LoadingAPI.ready` только после загрузки ассетов).

**Риск.** Невозможны headless-тесты физики и мира; на слабом телефоне белый экран
на 1–2 с; неверный порядок SDK ломает модерацию.

**Рекомендация.** `app/bootstrap.ts` c явным `async bootstrap(config)` и шагами
(ARCHITECTURE §6), генерация — `createWorld(seed)` по требованию, скрытие лоадера —
после первого отрисованного кадра/`ready()`. Экспортировать чистые функции
(`createWorld`, `updateVehicle`) для тестов.

### R-08 — Low. Магия чисел

`src/main.ts:9–13` (`STEP`, `BLOCK_STEP`, `GRID`, `BOUND`),
`src/main.ts:49–60` (`VIEW_HEIGHT`, позиция камеры),
`src/main.ts:205–213` (`tuning`), `src/main.ts:306` (радиус 1.8),
`src/main.ts:315` (`* 3.6`), `src/main.ts:322` (damping 6)

**Проблема.** Нарушает правило «числа баланса и тюнинга — в конфигах». Часть
чисел — не баланс, а геометрия (3.6 — перевод м/с в км/ч), и её место в `core/math.ts`.

**Риск.** Тюнинг требует правок кода; невозможно сравнить две машины; QA не может
подкрутить параметр без сборки.

**Рекомендация.** `config/tuning.json` (шаг, лимиты подшагов, ячейка хэша),
`config/world.json` (размер квартала, сид, плотность), `config/vehicles.json`
(спек `sedan`). `3.6` — хелпер `msToKmh` в `core/math.ts`.

### R-09 — Low. Дублирование данных и лишние объекты

`src/main.ts:89–93` (плиты), `src/main.ts:126–127` (ещё одна `BoxGeometry(1,1,1)`),
`src/main.ts:146–168` (массив объектов разметки)

**Проблема.** `plateGeo` и `buildingGeo` — две одинаковые единичные коробки;
`buildings` и `colliders` описывают одни и те же дома параллельно, поэтому
расхождение неизбежно. Разметка строится массивом объектов ради одного
`InstancedMesh`.

**Риск.** Данные города расходятся с коллизиями (машина «въезжает» в дом без
столкновения); лишние draw calls и мусор при генерации.

**Рекомендация.** Один источник — `Chunk` из `world` (здания, коллайдеры, разметка
как типизированные примитивы); `render/cityView.ts` строит меши из чанка, включая
единичную геометрию-прототип. Число инстансов известно заранее из данных.

### R-10 — Low. Resize и viewport

`src/main.ts:395–404`

**Проблема.** Размер берётся из `window`, а не из контейнера `#game`: в iframe
Яндекса/VK и при появлении мобильных панелей это разные числа. `devicePixelRatio`
пересчитывается только на `resize`, поэтому перенос окна на монитор с другим DPR
не учитывается. Обработчик не троттлится.

**Риск.** Размытая картинка или обрезанные края на мобилке, лишние вызовы
`setSize` при ресайзе окна.

**Рекомендация.** `render/scene.ts` → `viewport`: `ResizeObserver` на контейнере,
`matchMedia('(resolution: Xdppx)')` для смены DPR, `renderer.setSize(w, h, false)`,
пересчёт ортокамеры от размера контейнера.

## Что уже сделано хорошо (не ломать при переносе)

1. Ортокамера настроена корректно (aspect в фрустуме, `updateProjectionMatrix`).
2. Город на `InstancedMesh` — правильный подход, draw calls низкие.
3. Единый `dummy: THREE.Object3D` переиспользуется для матриц — без аллокаций.
4. `mulberry32` детерминирован, сид фиксирован.
5. Ручник реализован через экспоненциальное затухание боковой скорости
   (`lateral *= Math.exp(-grip * dt)`) — стабильно при любом `dt`, формулу можно
   переносить в `vehiclePhysics` как есть.
6. Кламп `dt` и защита от `lastTime === 0` уже есть — база для ADR 0002.

## Примечание: сверка с параллельной работой `core`

На момент ревью в `src/core/` уже появились `math.ts`, `rng.ts`, `spatialHash.ts`,
`events.ts`. Сверка с контрактом (`docs/ARCHITECTURE.md` §3):

| Что | Состояние | Действие |
|---|---|---|
| `Rect` / `Collider` / `Contact`, `circleRect`, `rectRect`, `lerpAngle` | совпадает, ноль аллокаций в hot-path | зафиксировано в ADR 0003 |
| `SpatialHash<T extends SpatialItem>` | совпадает (id, ячейка 8 м, stamp) | — |
| `EventBus` как класс (`on/off/emit/clear`) | структурно совместим с контрактом | до M6 добавить `once`, `listenerCount` |
| `EventBus.emit` без `try/catch` | расходится с правилом 4 §3.7 | один сломанный UI-обработчик остановит рассылку |
| `gameLoop` (`loop.ts`) | ещё не создан | контракт §3.1 в силе |
| `registry.ts` (`pool.ts`) | ещё не создан | контракт §3.3 в силе |

Это не блокер: контракт допускает реализацию классом, а `once`/`listenerCount`
нужны только к M6. Отмечено, чтобы `qa` не считал их забытыми в M2.
