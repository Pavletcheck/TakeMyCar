# ADR 0002 — Фиксированный шаг 60 Гц и интерполяция рендера

- **Статус:** принято
- **Дата:** 2026-11-23
- **Этап:** M1
- **Связано:** ADR 0001 (стек), `docs/ARCHITECTURE.md` §3.1 и §3.3
- **Заменяет / заменено:** —

## Контекст

В прототипе `src/main.ts` (M0.5) уже есть аккумулятор и шаг `1/60`, но:

- нет интерполяции: `carGroup.position` пишется прямо в фиксированном шаге
  (`src/main.ts:316–318`), поэтому на 120/144 Гц картинка «дробится», а на 30 fps
  на телефоне движение идёт рывками;
- пауза — один булев флаг, `blur` и `visibilitychange` перетирают друг друга
  (`src/main.ts:345–353`), а платформенная пауза (реклама, `game_api_pause`)
  вообще не учтена;
- переполнение подшагов не отслеживается, аккумулятор может «догонять» после
  подвисания или после возврата из фоновой вкладки.

При этом физика аркадная и нестабильна при больших `dt`: интегрирование по
переменному шагу даёт разные результаты на 30 и 144 Гц (дрифт «плывёт»,
машина на 30 fps проходит сквозь угол). Для портфолио также нужен детерминизм —
одинаковый ввод должен давать одинаковое поведение, чтобы багрепорты
воспроизводились.

## Рассмотренные варианты

### A. Переменный `dt` с клампом — отклонено

`dt = min(now - prev, 0.05)` и интегрирование напрямую.

- Плюсы: минимум кода, нет задержки ввода.
- Минусы: результат зависит от fps; на 144 Гц одни и те же действия ведут себя
  иначе, чем на 60; при просадке до 20 fps туннелирование сквозь тонкие стены;
  детерминизма нет, реплеи невозможны.
- Отклонено: несовместимо с требованием «одинаково приятно на телефоне и десктопе».

### B. Фиксированный шаг 120 Гц — отклонено

- Плюсы: точнее физика, меньше ошибка интегрирования.
- Минусы: двойная стоимость логики (бюджет 4 мс на шаг), для аркадной модели
  с курсом и боковым трением 60 Гц достаточно; на слабых мобилках — риск.
- Отклонено: цена без выигрыша в ощущениях.

### C. Фиксированный шаг 60 Гц + интерполяция рендера — **выбрано**

Классическая схема «Gaffer on Games»: аккумулятор, N подшагов по 1/60, остаток
превращается в `alpha ∈ [0,1)`; рендер интерполирует предыдущее и текущее
состояние.

- Плюсы: стабильная физика, плавная картинка на любом мониторе, детерминизм,
  простой бюджет (каждый шаг одинаковый).
- Минусы: визуальная задержка до одного шага (~16 мс) — для аркады приемлемо
  и компенсируется упреждением камеры; нужны `prev`-состояния и аккуратная
  работа с телепортами.

### D. Полу-фиксированный шаг (подшаги «по требованию») — отклонено

Дробление `dt` на равные части, но с переменным размером. Убирает задержку,
но сохраняет недетерминизм варианта A. Отклонено.

## Решение

1. **Шаг симуляции — ровно 1/60 с**, константа `FIXED_STEP` в `core/loop.ts`.
   Все системы получают только его.
2. **Максимум 5 подшагов на кадр** (`MAX_SUBSTEPS`): 83 мс симуляции за кадр.
   Остаток сверх этого **отбрасывается**, а не копится: игра замедляется вместо
   «спирали смерти». Факт отбрасывания инкрементит счётчик `overrun` в debug-HUD.
3. **`maxFrameDelta = 0.25 с`**: после сна ноутбука, фоновой вкладки или
   блокировки экрана время не догоняется, аккумулятор обнуляется.
4. **`alpha = accumulator / FIXED_STEP`**, передаётся в `onRender(alpha, frameDelta)`.
   Рендер считает `lerp(prev, cur, alpha)` для позиции и **кратчайшую** дугу для
   курса: `prevHeading + shortestAngle(cur - prev) * alpha`.
5. **У каждой сущности есть `prev`-состояние** (`prevX`, `prevZ`, `prevHeading`
   в `Transform2D`). Система обязана записать `prev` **до** интегрирования,
   иначе картинка «дёргается» на один шаг.
6. **Камера обновляется в `onRender`**, но цель берётся из интерполированного
   состояния игрока; сглаживание — экспоненциальное от `frameDelta`, не от `dt`.
7. **Пауза — набор причин** (`PauseReason`), см. ARCHITECTURE §3.1.
   При появлении хотя бы одной причины: цикл не вызывает `onFixedUpdate`,
   аккумулятор = 0, `onRender` продолжает вызываться (нужен для меню и рекламы).
8. **Фронты ввода (`wasPressed`/`wasReleased`)** существуют один фикс. шаг.
   `input.update()` вызывается один раз на кадр до подшагов, `beginTick()` —
   перед каждым.
9. **Порядок систем внутри шага фиксирован** (ARCHITECTURE §2). Менять порядок —
   значит менять поведение, это фиксируется в ADR или в ревью.
10. **Телепорты и спавн**: при появлении/переносе сущности `prev = cur`
    в том же тике, иначе рендер интерполирует «через полкарты».

## Эталонная реализация цикла

```ts
// src/core/loop.ts — эскиз, не копировать в обход контракта
let accumulator = 0;
let last = 0;

function frame(now: number): void {
  const frameDelta = last === 0 ? 0 : Math.min((now - last) / 1000, MAX_FRAME_DELTA);
  last = now;
  if (pausedBy.size === 0) {
    accumulator += frameDelta;
    let steps = 0;
    while (accumulator >= FIXED_STEP && steps < MAX_SUBSTEPS) {
      input.beginTick();
      for (const sys of systems) sys.fixedUpdate(FIXED_STEP);
      registry.flush();
      accumulator -= FIXED_STEP;
      steps += 1;
      tick += 1;
    }
    if (accumulator >= FIXED_STEP) {
      accumulator = 0;
      overrun += 1;
    }
    const alpha = accumulator / FIXED_STEP;
    input.endFrame();
    for (const r of renderers) r.render(alpha, frameDelta);
  } else {
    accumulator = 0;
    for (const r of renderers) r.render(0, frameDelta);
  }
}
```

## Последствия

Положительные:

- Одинаковый «характер» машины на 30, 60, 120 и 144 Гц.
- Детерминизм: при одинаковом потоке ввода состояние на тике `N` совпадает.
  Это основа реплеев и воспроизводимых багрепортов в M9.
- Простой бюджет: 4 мс на шаг, одинаковый для всех кадров.
- Пауза корректно переживает рекламу, blur и меню.

Отрицательные / цена:

- Появляется `prev`-состояние у сущностей: +12 байт на сущность и обязательный
  порядок записи в системах. Забыли записать `prev` — визуальный баг, а не ошибка
  типов. В ревью-чеклист добавлено.
- Визуальная задержка до 16 мс; компенсируется упреждением камеры по скорости.
- Интерполяция курса требует нормализации угла, иначе машина «крутится» на 359°.
- Спавн/телепорт требуют явного `snap`, иначе объект «въезжает» из прошлой точки.

Правила, которые нельзя нарушать:

1. **Нет физики в `onRender`.** Рендер только читает и интерполирует.
2. **Нет `performance.now()`/`Date.now()` в системах.** Время — только аргумент.
3. **Нет масштабирования `dt`** («слоу-мо» через `dt * 0.5`). Для слоу-мо
   масштабируется число подшагов, а не шаг.
4. **Нет `await` внутри шага.** Асинхронность — только в `app` и загрузке ассетов.
5. **Нет аллокаций в шаге**: `out`-массивы, пулы, переиспользуемые векторы.

## Проверка

- `npm run dev`: на мониторе 144 Гц машина едет плавно, без «двоения».
- Chrome DevTools → Performance → CPU 6× throttle: движение замедляется,
  но не телепортируется и не дёргается.
- Свернуть вкладку на 30 с, вернуться: нет рывка, `overrun` не растёт лавиной.
- Открыть меню (M6) и рекламу (M8): цикл на паузе, сцена продолжает рисоваться.
- Перезапуск миссии: число подписчиков событий не растёт (нет утечки).
