# ADR 0001 — Стек: TypeScript + Vite + Three.js, ортокамера, своя физика

- **Статус:** принято
- **Дата:** 2026-11-23
- **Этап:** M0 → M1
- **Контекст-файлы:** `AGENTS.md`, `docs/CONCEPT.md`, `docs/ROADMAP.md`
- **Заменяет / заменено:** —

## Контекст

TakeMyCar — браузерная 3D-игра в духе GTA 2: вид сверху, один район 1.2×1.2 км,
трафик, пешеходы, полиция, погони. Цели — портфолио и публикация на Яндекс Играх
(основная площадка) и VK Играх (адаптер).

Ограничения, которые задают выбор:

1. **Статический хостинг.** Яндекс Игры требуют игру в архиве, все ассеты локально,
   ноль внешних запросов в рантайме (CDN, шрифты, API) — см. `промпты/09_PLATFORM_QA.md`.
   Бандл < 25 МБ gzip, архив < 100 МБ.
2. **Бюджеты производительности.** 60 fps на десктопе 1080p, ≥30 fps на среднем
   телефоне; < 150 draw calls, < 200 000 треугольников.
3. **Вид сверху.** Камера ортографическая, логика полностью в плоскости XZ,
   вертикаль нужна только визуально (высоты зданий, тени). Это резко упрощает физику.
4. **Команда — ИИ-агенты.** Нужны предсказуемые API, минимум «магии», строгая
   типизация и отсутствие редактор-зависимых workflow.
5. **Контент — low-poly, flat shading.** Фотореализм не нужен, тяжёлые PBR-пайплайны
   и постобработка не окупаются.

## Рассмотренные варианты

### A. Three.js + Vite + TypeScript + собственная аркадная физика — выбрано

- Three.js ~0.187: WebGL2-рендерер, `InstancedMesh`, ортокамера, тени, GLTFLoader.
  Размер ядра — сотни КБ min+gzip, что укладывается в бюджет.
- Vite 8: мгновенный dev-сервер, статический билд без Node в рантайме, честный
  code splitting для ленивой загрузки SDK платформ.
- Физика своя: OBB/AABB/circle + spatial hash. Для вида сверху этого достаточно,
  поведение полностью контролируется и тюнится под «приятно в руках».

### B. Babylon.js

Плюсы: богатый тулинг, встроенные тени/материалы, есть физические плагины.
Минусы: движок заметно крупнее, API избыточен для ортокамеры и 3–5 материалов,
меньше примеров для top-down аркады, сложнее удержать бандл в бюджете.
Отклонено: избыточная масса при наших задачах.

### C. PlayCanvas

Плюсы: лёгкий движок, хорошая производительность на мобилках.
Минусы: workflow завязан на редактор/облако, что плохо для агентов и офлайн-сборки;
ручное кодирование сцены без редактора неудобно. Отклонено.

### D. PixiJS / 2.5D-спрайты

Плюсы: минимальный вес, максимальная простота, отличный fps.
Минусы: теряется объём — высоты зданий, тени, поворот камеры на 90°, LOD моделей.
Концепт прямо требует «GTA2-подобный объём» (наклон камеры, тени). Отклонено.

### E. Готовый физический движок (Rapier / Cannon / ammo.js)

Плюсы: корректные коллизии из коробки, меньше своего кода.
Минусы: WASM/большой бандл (Rapier ~1 МБ wasm), детерминизм между браузерами не
гарантирован, аркадную «приятность» всё равно настраивать вручную, а логика в 2D
делает SAT/AABB тривиальным. Отклонено на старте; возврат возможен только новым ADR.

### F. Webpack / esbuild вместо Vite

Vite выигрывает по скорости dev-цикла и простоте статического билда; у esbuild
нет dev-сервера с HMR из коробки. Отклонено.

## Решение

1. **TypeScript strict** (`strict`, `noUnusedLocals`, `noUnusedParameters`,
   `noImplicitOverride`, `verbatimModuleSyntax`) — уже включено в `tsconfig.json`.
2. **Vite 8** как сборщик; базовый путь прод-сборки — `/TakeMyCar/` через
   `VITE_BASE`; никаких внешних плагинов, тянущих сеть.
3. **Three.js** — единственная графическая зависимость. Запрещено использовать
   примеры/аддоны, которые требуют внешних ассетов из сети.
4. **Ортографическая камера сверху** с небольшим наклоном:
   `OrthographicCamera(-h*aspect/2, h*aspect/2, h/2, -h/2, 0.1, 500)`,
   `VIEW_HEIGHT ≈ 62 м`, позиция `y ≈ 72`, смещение `z ≈ 40` (наклон ~30°).
   Камера считает только параметры (позиция, зум, поворот, тряска) в `core/camera.ts`;
   применение к объекту Three — в `render`.
5. **Своя физика**: формы `circle`, `aabb`, `obb`; SAT для OBB-OBB, circle-OBB
   и circle-circle; решатель с restitution ≈ 0.2 и 2–4 итерациями; spatial hash
   с ячейкой 8 м. Никаких Rapier/Cannon/ammo.
6. **Логика в плоскости XZ.** Высота `y` — только визуал (меши, тени). Никаких
   гравитационных интеграторов и подвески на лучах.
7. **Только локальные ассеты.** Модели — GLB из Blender 5.3, текстуры — PNG/WebP
   из ComfyUI. Шрифты — локальные файлы. CDN запрещён.
8. **Смена стека — только новым ADR** и одобрением прораба.

## Последствия

Положительные:

- Все бюджеты достижимы: low-poly + инстансинг + ортокамера дают малый draw call
  count и предсказуемую загрузку GPU.
- Физика полностью наша: дрифт, ручник, PIT и «читаемые» столкновения тюнятся
  без борьбы с движком; никакого wasm-бандла.
- Логика не зависит от рендера, значит системы тестируются в Node без WebGL.
- Один язык (TS) и один сборщик для игры, HUD и тулинга.

Отрицательные / цена:

- Мы отвечаем за качество коллизий: нужны тесты на SAT, на «выталкивание из угла»,
  на стабильность стопки объектов. Это отдельная работа в M2.
- Three.js не даёт готового fixed step — цикл и интерполяция пишутся сами
  (см. ADR 0002).
- Тени в ортокамере требуют тесного shadow-фрустума вокруг игрока; при неверной
  настройке появляется «питер-пэннинг».
- Нет встроенного ECS/сериализации — реестр сущностей свой, намеренно простой.

Риски и меры:

| Риск | Мера |
|---|---|
| Просадки из-за количества мешей | `InstancedMesh` по типу, атласы, лимит draw calls в debug-HUD |
| Дрожание физики на 144 Гц | фиксированный шаг 60 Гц + интерполяция (ADR 0002) |
| Расползание бандла | запрет тяжёлых зависимостей, проверка размера в релиз-чеклисте |
| Несовместимость `@types/three` с версией | обе версии пинятся в `package.json` и обновляются вместе |
| Наклон камеры ломает сортировку/тени | наклон фиксирован конфигом; проверка на «сером полигоне» в M1 |

## Что подтверждает решение

- M1: серый полигон, куб едет по WASD, 60 fps, `typecheck`/`build` зелёные.
- M2: 300 статических + 50 движущихся коллайдеров без просадок ниже 60 fps.
- M4: круг по кварталу с ручником без застреваний.
- M8: архив проходит лимиты Яндекса, ноль внешних запросов в DevTools → Network.
